# fixtures/ics

The conformance set of the `.ics` module (docs/EVENTS.md §5.4, §5.6), shared by TypeScript
(`packages/core`) and C# (`windows/Thirteen.Core`, task W2). Generated by `pnpm fixtures` from
`packages/core/scripts/ics-*.ts`; never edit a file here by hand: `packages/core/test/ics/fixtures.test.ts`
fails until the committed files equal freshly generated ones, and the generator removes files it no
longer writes. `index.json` lists every case and procedure (`"complete": true`: ports fail on unknown
entries).

Inputs are anonymized copies of what other apps write, kept in `packages/core/scripts/ics-cases.ts` as
content lines so that their bytes (line ends, folds, a byte order mark) are exact; inputs "as Thirteen
exports them" are generated with the engine. `.gitattributes` and `.editorconfig` here keep every byte
as written.

## Layout

```
index.json                  the manifest: version, complete, counts, every case and procedure file
cases/*.ics                 inputs
expected/*.json             per input: calendar fields, warnings, UID groups, expanded occurrences
roundtrip/*.ics             serializeICalendar(parseICalendar(input)) for every case
edits/*.json, edits/*.ics   edits applied to one UID group, and the exact document after each step
imports/*.json, *.ics       a target document, the files imported into it in order, the exact documents
restore/                    two local calendars and a subscription as Thirteen exports them, the same
                            as one zip, an earlier export, and restore.json with the exact results
```

## How to run a case

Every value that needs zone data is computed through the `RecordedZoneResolver` built from the
`zoneOffsets` of `fixtures/events.json` (§5.5), never through the platform's own zone data.

- Read `cases/{name}.ics` with `parseICalendar(text, { calendarId, zones })`, `calendarId` being the file
  name without `.ics` (it seeds derived UIDs and is the first part of every occurrence key). Compare
  `calendar` (`name`, `color`, `refreshInterval`, the calendar properties in `extra`, the
  `VTIMEZONE`s read with their observance count, the components kept as read in `others`),
  `warnings` and `groups`.
- For each entry of `expansions`, compare `expandCalendar(calendar, deviceZone, zones, window, 'ifc',
  { calendarId })` (`eventsFromCalendar` plus its warnings) with `occurrences` and `warnings`.
  Every case is expanded in Europe/Tallinn and America/New_York from 2026-01-01T00:00 to
  2027-12-31T24:00; cases about other years add their own windows and device zones.
- `roundtrip/{name}.ics` is `serializeICalendar(calendar, zones, { now: "2026-10-19T06:41" })`, byte for byte.
  For "as read" cases it equals the input with CRLF line ends and without a byte order mark; for the
  others it is that plus a generated `VTIMEZONE` for each zone the input uses without defining it.

JSON forms (as in `fixtures/events.json`, §5.5): dates `"YYYY-MM-DD"`, wall clocks `"YYYY-MM-DDTHH:MM"`;
`IcsDateValue` as `{"kind":"date","date"}`, `{"kind":"floating"|"utc","value"}` or
`{"kind":"zoned","value","tzid"}`; `IcsEvent` with every field of §5.4 except `raw` and `original`, in
declaration order, `rrules` and `exrules` as their canonical `formatRRule` text, `line` the 1-based line
the component begins on; properties as `{"name","params":[[name, value]],"value"}` exactly as written;
warnings as `{"line","code","detail"}` (`detail` is informative: compare `line` and `code`);
occurrences as `EventOccurrence` JSON `{"key","calendarId","title","allDay","start","end"}`, keys per
§3.2.

## Procedures

A procedure file holds scenarios. A scenario starts from a file of this set (`{"file"}`) or from a new
empty Thirteen calendar (`{"new": {"calendarId","name","color"}}`, `newICalendar` written at `now`), and
each step starts from the previous step's expected document, read with `parseICalendar(text,
{ calendarId, zones })`. After the step, `serializeICalendar(calendar, zones, { now })` must equal the
step's `expected` file byte for byte; steps with `expansions` also give the occurrences of that document.

- `edit`: `changes` applied in order. `set` replaces the given fields (JSON as above) of one member of
  a UID group (the master when `recurrenceId` is null); `untils` rewrites the `UNTIL` of the listed
  rules of the master with `withRetimedUntils` (`{"rule","index","endDate"}`, after the `set` before it);
  `add` adds a new group whose master is the given event; `remove` removes a group. Every touched group
  goes through `replaceGroup`, so it is re-serialized, the properties of untouched fields as read
  (§4.9). The field values are the ones the platform computes (`retimeExceptions`, `allDayEnd`,
  `untilFor`, `SEQUENCE` plus one and `LAST-MODIFIED` at `now` for a user change).
- `import`: the file imported into the calendar (below); `result` gives the UID groups counted
  (§2.17 step 4).
- `restore`: the file restored into the calendar (below); `result` gives the backup's UID groups
  counted.

### Edits

- `edits/generated-tz-grow.json`: Events added to a document whose generated VTIMEZONE records the years 2026 to 2027 (cases/ny-open-ended.ics): a 2031 America/New_York event rebuilds it as X-THIRTEEN-GENERATED:2026-2031 (still open-ended), then a 2005 event adds the pre-2007 rule period (2005-2031, onsets from 2004). Every other group stays byte for byte.
- `edits/outlook-edit-one.json`: cases/outlook-publish.ics with one event's title changed in Thirteen (SEQUENCE incremented, LAST-MODIFIED set): only that UID group is re-serialized (the properties of untouched fields as read); every other group, the Windows zone ids and Outlook's VTIMEZONE stay byte for byte.
- `edits/own-time-rdate.json`: The Consultation series of cases/rrule-rdate.ics: weekly at 09:00 with an RDATE at 15:00 on Monday, November 2, a day the rule also produces (both are read). "Delete this event only" on the 15:00 occurrence adds EXDATE;TZID=Europe/Tallinn:20261102T150000 (the 09:00 occurrence stays); then a retime of the series to 10:00 (retimeExceptions, minuteDelta 60) rewrites that EXDATE and the RDATE to 16:00, the PERIOD RDATE to 15:00 and the EXDATE at the series time to 10:00.
- `edits/retime-until.json`: The Outlook-style choir series of cases/outlook-publish.ics (FLE Standard Time, UNTIL=20261116T170000Z at the last occurrence's start, November 16 at 19:00 in Tallinn) moved to 19:30: retimeExceptions lists its UNTIL, which becomes 20261116T215959Z (the end of November 16 there, so November 16 stays); every other byte of the rule and of the other groups stays as read. Then toggled to all-day (UNTIL=20261116, EXDATE;VALUE=DATE) and back to timed (a UTC end of day again).
- `edits/year-9999.json`: New all-day events at the end of the range (§3.1.1): one on 9999-12-31 (one day: no DTEND) and one from 9999-12-29 to 9999-12-31 (DURATION:P3D), both read back as ending 9999-12-31T24:00.

### Imports

- `imports/baseline.json`: Import baselines (§2.17 step 3, §3.6). A Google export imported into a new calendar (each group gets X-THIRTEEN-IMPORTED-LAST-MODIFIED in its raw text), edited in Thirteen, then a newer export (its version is later than the baseline: it replaces the edited group) and an older one (unchanged). And a Google export over two events created in Thirteen with the same UIDs and no baseline: the newer version wins either way.
- `imports/customized-tz.json`: Two Outlook files whose different VTIMEZONEs are both named "Customized Time Zone" (UTC+05:30, and UTC-03:00 with DST), imported one after the other into one calendar: the second is renamed "Customized Time Zone (2)", its group re-serialized with the new TZID, and its event keeps its time. A third file with the same definition as the first shares it (nothing renamed, raw text kept).
- `imports/known-tz.json`: Known zone ids are never renamed (§3.6). A calendar holding an event made in Thirteen in Europe/Tallinn (with its generated VTIMEZONE for 2026), then a Google export and an Apple export that both use Europe/Tallinn with their own, different VTIMEZONEs: nothing is renamed, every imported group is stored byte for byte (plus its baseline line), and the document keeps one Europe/Tallinn VTIMEZONE, Thirteen's, rebuilt for the years the imported events reach (2026-2027, then 2025-2027). The same imports into an empty calendar keep the Google file's VTIMEZONE.
- `imports/missing-uid.json`: cases/missing-uid.ics imported twice into the same calendar: the derived UIDs come from the target calendar's id, so the second import finds both groups unchanged and adds nothing.
- `imports/override-only.json`: An invited single instance (cases/override-only.ics: an override without its master). Imported on top of cases/google-secret.ics it merges into the stored master (the group counts as updated; the master stays byte for byte; the override carries its own baseline). After that override is edited in Thirteen, an older copy of the file is unchanged (the edit stays) and a newer one replaces it (the stored master byte for byte). Into an empty calendar it is stored as read, counted as added and shown as a single event (the orphan path).

How an import merges (§2.17 step 3, §3.6; `importCalendar` in `packages/core/scripts/ics-procedures.ts`):

1. Read the file with the target calendar's id; rename its file-defined zones that the target defines
   differently (`renameCollidingTimeZones`).
2. Several masters with one UID: the newest (`groupVersion`, the first of equals) is used, the others
   count as skipped.
3. A group whose UID is new to the target is added with its raw text and the baseline line
   `X-THIRTEEN-IMPORTED-LAST-MODIFIED` (`withImportBaseline` with its `groupVersion`).
4. A group whose UID the target holds replaces it when its version is later than the stored group's
   baseline, or, when the stored group has none, than the stored group's own version; otherwise it
   counts as unchanged.
5. A group without a master merges override by override: a new `RECURRENCE-ID` is added, a stored
   override is replaced by the rule of step 4 applied to that override; each added or replaced override
   carries its own baseline; the stored master is never touched. The group counts as updated when
   anything changed.
6. The target keeps its `VTIMEZONE` of a `TZID` and takes the incoming one of a `TZID` it lacks
   (`mergeTimeZones`); the writer drops unused ones and rebuilds generated ones whose years grew.

Added and replaced groups keep their raw text (`replaceGroup` with `keepRaw`).

### Restore

- `restore/restore.json`: Restore of Thirteen's own exports (§2.17 "Restore"): version against version, baselines ignored and none added, nothing deleted. Personal.ics restored into a store without it becomes a new calendar that keeps the file's id, name and color, with the file's groups; restored again, it leaves that one calendar unchanged. older.ics, an earlier export of the same calendar, restored over the calendar edited since: the Dentist event edited since is kept (counted as kept newer), the Piano lesson deleted since comes back, the Passport renewal created since stays.

`restore/` holds `Personal.ics` and `Work.ics` (local calendars) and `Holidays in Estonia.ics` (a
subscription: its last fetched copy with `X-THIRTEEN-SUBSCRIPTION-URL` and
`X-THIRTEEN-SUBSCRIPTION-INTERVAL`), each with its `X-THIRTEEN-CALENDAR-ID`, name and color, and
`Thirteen calendars 2026-10-19.zip`, the same three files as the web export writes them: an
uncompressed zip (stored entries, UTF-8 names, dated 2026-10-19 09:41). `restore.json` lists them as the
restore dialog does (`calendars`). A restore merges version against version (`restoreCalendar`):
a group only in the backup is added, a group in both is replaced when the backup's `groupVersion` is
later and counted as kept newer when the calendar's is later, a group only in the calendar stays;
baselines are ignored and none are added.

## ical.js

`packages/core/test/ics/oracle.test.ts` expands every case with `ical.js` 2.2.1 (its zone registry
holding only the round-trip text's own `VTIMEZONE`s) and requires the same occurrences in every window of
`expected/`, on a UTC device. Where `ical.js` does not implement RFC 5545 or §5.4 the test lists the
UID and the reason.
