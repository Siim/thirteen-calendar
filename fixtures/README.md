# Golden fixtures

The engine's golden files: the contract between `@thirteen/core` (TypeScript, normative) and its Swift,
Kotlin and C# ports. Every file here is generated by `pnpm fixtures` from `packages/core/scripts`; never
edit one by hand. Each has a staleness test in `packages/core/test` that regenerates it in memory and
compares it with the committed file, so `pnpm test` fails until you rerun `pnpm fixtures`. Ports read
the files in place, from the repository root; none keeps a copy.

| File | What it pins | Spec | Generator (`packages/core/scripts/`) | Staleness test (`packages/core/test/`) | Read by |
|---|---|---|---|---|---|
| `conversions.json` | the calendar engine | docs/SPEC.md §4.2 | `fixtures.ts` | `fixtures.test.ts` | Swift `FixtureParityTests`, Kotlin `FixtureParityTest`, C# `FixtureParityTests` |
| `events.json` | the events engine | docs/EVENTS.md §5.5 | `events-fixtures.ts`, `recurrence-fixtures.ts`, `layout-fixtures.ts`, assembled by `events-file.ts` | `events/fixtures.test.ts` | the TS tests; Swift `EventsFixtureParityTests`, Kotlin `EventsFixtureParityTest`, C# `EventsFixtureParityTests` (§5.1) |
| `ics/` | the `.ics` module | docs/EVENTS.md §5.6 | `ics-fixtures.ts` and the other `ics-*.ts` | `ics/fixtures.test.ts` | the TS tests; C# `IcsConformanceTests` (§5.1) |
| `mockup/mockup-events.json` | the mockup data set | docs/EVENTS.md §6.7 | `mockup-events.ts` | `events/fixtures.test.ts` | every fake store and screenshot run (§6.7) |

`packages/core/scripts/generate-fixtures.ts` writes all of them, each only when its content changed, and
removes files under `ics/` that it no longer writes. A second run reports every file "Unchanged".

After a change to `@thirteen/core`:

```sh
pnpm fixtures                                      # regenerate every file here
pnpm test                                          # TS suites, including the staleness checks
pnpm apple:test                                    # Swift parity tests (swift test in apple/ThirteenKit)
(cd android && ./gradlew :core:test)               # Kotlin parity tests
(cd windows && dotnet test)                        # C# parity and .ics conformance tests
```

## conversions.json

fixtures/conversions.json is format version 2 (594,977 bytes). The top-level object is pretty-printed, as are the objects directly inside it (gregorianCalendar, formats, labelLookups, arithmetic). Every array element at those levels is one compact JSON value on its own line. The file ends with a newline. Keys appear in this order; all ThirteenDate JSON uses the key order {kind, system, year, month, day} or {kind, system, year, id}, and `year` is always the Gregorian year.

{
  "version": 2,
  "generatedBy": "@thirteen/core",
  "spec": "docs/SPEC.md",
  "systems": [ CalendarSystem JSON verbatim (id, name, shortName, inventor, proposedYear, summary, history[{year,text}], weekStartsOn, yearOffset, months[{index,name,shortName,gregorianNameEquivalent,meaning?}], intercalaryDays[{id,code,name,shortName,description,leapOnly,afterMonth,dayOfYear:{common,leap}}]) + "displayYearRange": {"min","max"} ],   // IFC, then Positivist
  "gregorianCalendar": { name, shortName, inventor, proposedYear, summary, history[], months[{index,name,shortName,narrowName}] },
  "cases": [ FixtureCase ... ],           // 1620 cases: every day of 2024 and 2026, plus boundary days (01-01, 01-02, 02-28, 02-29, 03-01, 06-16..06-19, 12-29..12-31) of 1, 1600, 1900, 2000, 2023, 2100, 9999. Date-major, IFC then Positivist.
  "comparisons": [ exact Comparison JSON (gregorian as {year,month,day}, keys in SPEC §3 order) + "displayYear" + "daysUntilYearDay" ],   // 34 dates × 2 systems
  "formats": {
    "options": [ {}, {"style":"long"}, {"style":"long","includeYear":false,"includeWeekday":false}, ... ],   // 21 bags: {} first, then for each style: {style} and includeYear × includeWeekday
    "thirteen": [ {"date": ThirteenDate, "outputs": [21 strings, outputs[i] = formatThirteen(date, options[i])]} ],
    "gregorian": [ {"date": {"year","month","day"}, "outputs": [21 strings]} ]
  },
  "numericParsing": [ {"system", "text", "expected": ThirteenDate | null} ],   // null = parseThirteen throws
  "yearStats": [ exact YearStats JSON ],            // years 1, 1900, 2000, 2023, 2024, 2026, 9999 × ifc, positivist
  "monthAlignments": [ exact MonthAlignment JSON ], // 2024 and 2026 × 2 systems
  "thirteenYearLayouts": [ {"year","system","displayYear","isLeapYear","daysInYear","weekdays":[..7],"months":[{"month","first":"YYYY-MM-DD","last":"YYYY-MM-DD","gregorianMonthStarts":[[thirteenDay, gregorianMonth],...]}],"intercalary":[{"id","afterMonth","gregorian":"YYYY-MM-DD","dayOfYear","gregorianWeekday"}]} ],
  "gregorianMonthLayouts": [ {"year","month","system","weekStartsOn","leadingBlanks","rows","thirteenMonthStarts":[gregorian days],"intercalaryDays":[gregorian days]} ],   // 2024, 2026 × 2 systems × 12 months × weekStartsOn 0 and 1
  "slots": [ {"year","system","slots":[{"kind":"month","month":1} | {"kind":"intercalary","id":"leap-day"}, ...]} ],
  "labelLookups": {
    "gregorian": [ {"system", "gregorian":{y,m,d}, "fallsOn":ThirteenDate, "sameLabel":ThirteenDate|null, "sameLabelFallsOn":{y,m,d}|null} ],
    "thirteen":  [ {"thirteen":ThirteenDate, "fallsOn":{y,m,d}, "sameLabel":{y,m,d}|null, "sameLabelFallsOn":ThirteenDate|null} ]
  },
  "notableDates": [ {"year","system","dates":[{"id","gregorian":{y,m,d},"thirteen":ThirteenDate,"sameLabel":ThirteenDate|null}]} ],
  "arithmetic": {
    "addDays":       [ {"from":ThirteenDate,"days":n,"expected":ThirteenDate|null} ],    // null = throws
    "addMonths":     [ {"from":ThirteenDate,"months":n,"expected":ThirteenDate|null} ],  // null = throws
    "sameSlotInYear":[ {"from":ThirteenDate,"year":n,"expected":ThirteenDate|null} ]     // null = returns null
  }
}

FixtureCase keys, in order: gregorian (ISO string), thirteen (ThirteenDate incl. system), displayYear, dayOfYear, isLeapYear, gregorianWeekday, thirteenWeekday (or null), weekdayShift (or null), labelDrift (or null), formattedLong.

Example case (2026-10-19, IFC):
{"gregorian":"2026-10-19","thirteen":{"kind":"month","system":"ifc","year":2026,"month":11,"day":12},"displayYear":2026,"dayOfYear":292,"isLeapYear":false,"gregorianWeekday":1,"thirteenWeekday":4,"weekdayShift":3,"labelDrift":7,"formattedLong":"October 12, 2026"}

Example comparisons entry (2024-12-31, Positivist):
{"gregorian":{"year":2024,"month":12,"day":31},"thirteen":{"kind":"intercalary","system":"positivist","year":2024,"id":"leap-day"},"dayOfYear":366,"isLeapYear":true,"gregorianWeekday":2,"thirteenWeekday":null,"weekdayShift":null,"labelDrift":null,"gregorianMonthDays":31,"thirteenMonthDays":null,"daysIntoYear":365,"daysRemainingInYear":0,"yearProgress":0.9972677595628415,"displayYear":236,"daysUntilYearDay":365}

## events.json

The golden file of the events engine (docs/EVENTS.md §5.5, which is normative for its content). Format
version 1. Same layout rules as `conversions.json`: a pretty-printed envelope, one compact JSON value per
array element on its own line, a trailing newline. Top-level keys, in order:

```
{
  "version": 1,
  "complete": true,                 // every section of §5.5 is present; ports fail on unknown sections (removed at 1.0)
  "generatedBy": "@thirteen/core",
  "spec": "docs/EVENTS.md",
  "tzVersion": "2025b",             // Node's process.versions.tz when the content was generated
  "counts": { "localDateTimes": 29, ... },   // cases per section; every port asserts each count
  "localDateTimes": [...], "endForms": [...], "wallClock": [...], "zoneMath": [...],
  "rrules": [...], "rruleEquality": [...], "untils": [...], "dateLists": [...],
  "thirteenRules": [...], "ruleFromStart": [...], "expansions": [...], "endBefore": [...],
  "splits": [...], "retimes": [...], "seriesEdits": [...], "series": [...], "recognitions": [...],
  "presets": [...], "descriptions": [...], "nextOccurrences": [...], "repeatNotes": [...],
  "adaptations": [...], "drafts": [...], "newDrafts": [...], "merges": [...], "alarms": [...],
  "alarmInstants": [...], "chipTimes": [...], "monthColumns": [...], "monthLayouts": [...],
  "weekLayouts": [...], "dayLayouts": [...], "agendas": [...], "yearMarks": [...],
  "zones": [...], "zoneOffsets": [...]
}
```

The case shape of every section, the JSON forms of `RRule`, `ThirteenRule`, `EventRecurrence`,
`ExtraDate`, `OriginalDate` and the rest, and the case lists are in §5.5; JSON field names equal the
TypeScript field names of §5.2 (packages/core/API.md, "Events"). In short:

- Dates are `"YYYY-MM-DD"` strings and wall clocks `"YYYY-MM-DDTHH:MM"` strings, ends in end-of-day form
  (`"2026-10-19T24:00"`), unlike `conversions.json`, which uses date objects.
- An expected value of `null` means "throws" (`RangeError` in TypeScript), unless §5.5 gives `null` a
  meaning of its own for that field (for example `zonedToUtc` outside years 1 to 9999).
- Occurrences are `EventOccurrence` JSON: `{"key","calendarId","title","allDay","start","end"}`.
- `series` cases give the `SeriesInput` with every field, `duration` included (`null`, or
  `{"days","minutes"}` for a master whose length is an RFC 5545 `DURATION` with days), and each expected
  occurrence with its start instant, `startUtc` (`null` for all-day occurrences).

Where the generated cases differ from the §5.5 case list as written:

- `thirteenRules` `parts`: the weekly series from 2020 uses the 2035 horizon instead of 2033. With 400
  values per part, a third part needs 802 occurrences, so only a 2035 horizon shows the property §5.5
  describes (the second part grows to full, a third is appended, the first part is unchanged).
- `expansions`: each `thirteenRules` case is expanded over the first of the three windows that holds one
  of its occurrences (series that end outside all three over their own years), so no case is empty;
  separate cases run weekly and yearly 13-month rules through the 2099 to 2101 window and to 9999-12-31,
  and leap-only repeats past their cap.

Example, the first `untils` case (`UNTIL=20261116T165959Z` on a 19:00 Europe/Tallinn series: 18:59 there,
so the last original date that can start by then is November 15, and `formatUntil` of that date):

```
{"until":{"kind":"utc","value":"2026-11-16T16:59"},"zone":"Europe/Tallinn","startMinute":1140,"inZone":"2026-11-16T18:59","endDate":"2026-11-15","allDay":false,"text":"20261115T215959Z"}
```

**Zones.** Only `zones` tests a platform's own time zone data: every port runs it through its own
resolver (`FoundationZoneResolver`, `JavaTimeZoneResolver`, `WindowsZoneResolver`, the web's `Intl`
resolver) and core's `zonedToUtc`, and lists by case id, with the reason, any case its zone data cannot
answer as tzdata does. `zoneMath` uses a synthetic resolver built from each case's own table. Every other
section that needs zones (`untils`, `series`, `alarmInstants`), the mockup file and every `ics/`
expectation run through a `RecordedZoneResolver` built from `zoneOffsets` alone: the generator records,
while it computes those sections, the offset at the start of every zone and UTC year it is asked about
and each transition in that year, and the recorded resolver throws for a zone or year it does not hold.
So those expectations do not depend on a port's tzdata. `packages/core/scripts/zone-resolvers.ts` has
the TypeScript `recordedZoneResolver`; each port has its own `RecordedZoneResolver` in its test sources.

**tzVersion.** The zone cases use dates whose rules are settled history, so a newer Node changes at most
`tzVersion`. The generator then keeps the committed file, and the staleness test ignores `tzVersion`.
A port that fails a `zones` case prints `tzVersion` next to its own tzdata version.

**Size.** §5.5 sets a budget of 600 kB. The case lists of §5.5 currently produce about 695 kB, and
`events/fixtures.test.ts` holds the file under 700 kB until the budget is settled.

**Order of publication.** The Core team published the sections in the order of EVENTS.md §6.0 and then
marked the file complete. A section that grows changes its count in `counts`, which every port asserts.

## ics/

The conformance set of the `.ics` module (docs/EVENTS.md §5.6), shared by TypeScript and C# (the only
port of the module). [`ics/README.md`](ics/README.md) describes every case, how to run it, the JSON
forms and the procedures; `ics/index.json` is its manifest (`"version": 1`, `"complete": true`, the
counts, every case and procedure file), and C# fails on entries it does not know.

```
ics/
  index.json           manifest
  README.md            what each file tests and where it came from (anonymized)
  cases/*.ics          inputs, byte for byte as other apps write them (line ends, folds, a byte order mark)
  expected/*.json      per input: calendar fields, warnings, UID groups and expanded occurrences for
                       2026-01-01 to 2027-12-31 in Europe/Tallinn and America/New_York (some cases add
                       their own windows and device zones)
  roundtrip/*.ics      serializeICalendar(parseICalendar(input)) for every case
  edits/               edits applied to one UID group and the exact document after each step
  imports/             a target document, the files imported into it in order, the exact documents
  restore/             Thirteen's own exports (one file per calendar and the same as one zip), an
                       earlier export, and restore.json with the exact results
```

Everything that needs zone data runs through the `RecordedZoneResolver` of `events.json` (above).
`.gitattributes` and `.editorconfig` in `ics/` keep every byte of the inputs as written: never let an
editor or Git normalize their line ends. `packages/core/test/ics/oracle.test.ts` also checks every case's
occurrences against `ical.js` 2.2.1.

## mockup/mockup-events.json

The mockup data set of docs/EVENTS.md §6.7: one file that every fake store (Apple `FakeCalendarStore`,
Android `FakeCalendarRepository`, Windows `FakeEventStore`, web `MemoryEventStore`), every screenshot
run and the board in `design/events/mockups.html` load, so screens match across platforms. It is
generated from the rows in `packages/core/scripts/mockup-events.ts`; no team copies the table into
code. The `monthLayouts` case for IFC October 2026 in `events.json` (and the other layout cases built on
the mockup week) take their occurrences from the same rows.

Same layout rules as `events.json`. Top-level keys, in order:

```
{
  "version": 1,
  "generatedBy": "@thirteen/core",
  "spec": "docs/EVENTS.md",
  "now": "2026-10-19T09:41",         // the device's wall clock: Monday, October 19, 2026 (IFC Thursday, October 12)
  "deviceZone": "Europe/Tallinn",
  "window": { "from": "2026-01-01T00:00", "to": "2027-12-31T24:00" },
  "calendars": [ CalendarInfo JSON ],      // the six calendars of §6.7, in the Calendars list's order
  "events": [ CalendarEvent JSON + "rrule" + "marker" ],
  "occurrences": [ EventOccurrence JSON ]  // every occurrence in the window, device wall clock
}
```

- `calendars`: Home, Family, Work, Running club, Holidays in Estonia (subscribed, read only) and
  Birthdays (read only), with the accounts and colors of §6.7.
- `events`: each event as `CalendarEvent` JSON (§3.1: the `EventDraft` fields in the event's zone, then
  `id`, `status`, `readOnly`, `organizer`, `attendeeCount`, `alarmsEditable`, `selfStatus`), plus `rrule`,
  the one `RRULE` value the repeat is stored as on Apple and in `.ics` (`recurrenceToRRule`: a Gregorian
  rule, or a 13-month rule's encoding), and `marker`, the `X-THIRTEEN-RULE` value of a 13-month rule
  (both `null` when there is none). Every timed event is in `Europe/Tallinn`.
- Ids and keys use the Windows and web form of §3.2: `{calendarId}/{uid}` (`"home/book-club"`) and
  `{calendarId}/{uid}|{original start}` (`"home/rent|2026-01-01"`; a wall clock for timed events). A
  fake store for Apple or Android maps them to its own form if it needs to.
- `occurrences`: expanded with `expandSeries` and sorted by the order key of §5.3.

Example event:

```
{"title":"Book club: Cotsworth","location":"Raamatukoi","notes":"Chapter 4: Eastman's letters to the League of Nations.","url":"","allDay":false,"start":"2026-01-12T19:00","end":"2026-01-12T21:00","timeZone":"Europe/Tallinn","calendarId":"home","recurrence":{"rule":{"kind":"thirteen","rule":{"kind":"monthly","system":"ifc","day":12}},"end":{"kind":"never"},"extraDates":[],"exceptDates":[]},"alarms":[{"kind":"relative","offsetMinutes":-60}],"availability":"busy","id":"home/book-club","status":"confirmed","readOnly":null,"organizer":null,"attendeeCount":0,"alarmsEditable":true,"selfStatus":null,"rrule":"FREQ=YEARLY;BYYEARDAY=12,40,68,96,124,152,-186,-158,-130,-102,-74,-46,-18","marker":"SYSTEM=ifc;KIND=monthly;DAY=12"}
```
